# EDA 工具环境

[English](eda-env.md)

本指南说明如何为设计任务准备工具与资源，确认它们在 agent 的执行环境中可用，并定位环境问题。内容以 VeriPower 当前随附阶段使用的工具接口为依据。工具版本、库、模型和分析条件应根据实际硬件任务及已有工具环境选择。

## 1. 明确执行环境

阶段脚本以调用者的身份启动工具。执行进程需要能访问工作目录、源文件、库和模型文件，并有权限写入输出。VCS 生成的 `simv` 等可执行文件，也需要在兼容的运行环境中执行。

在 agent 实际执行命令的环境中加载工具配置。若使用环境脚本，应先在 shell 中加载该脚本，再从同一环境启动 Claude Code、OpenCode、DeepSeek Harness、Codex 等 agent harness。下例中的路径需替换为实际使用的环境脚本：

```bash
. "/path/to/site-eda-setup.sh"
```

环境配置应通过 `PATH` 提供所需命令，加载许可证设置，并使所选资源可访问。Synopsys 工具通常使用 `SNPSLMD_LICENSE_FILE` 或 `LM_LICENSE_FILE`；具体值以已有许可证配置或管理员提供的信息为准。

通过 agent 的执行工具检查配置是否生效。交互终端中能运行某个命令，并不代表另行启动的进程具有相同环境。子进程继承已导出的环境变量；Bash 读取哪些启动文件取决于调用方式，不能统一依赖 `~/.bashrc`。相关规则见 Bash 的[环境继承说明](https://www.gnu.org/software/bash/manual/html_node/Environment.html)和[启动文件说明](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)。

采用容器、远程执行或工具包装脚本时，应在工具实际运行的位置检查路径、权限、许可证访问及输出是否可见。这类集成需要保持阶段使用的命令接口，等待工具结束，并返回退出状态和输出。

## 2. 按工作准备工具

将 [requirements.txt](../requirements.txt) 中的 Python 依赖安装到阶段脚本使用的环境中。下表列出各类工作需要的工具能力。许可证应覆盖实际使用的功能，不能只确认工具能够启动。

| 工作 | 所需工具或能力 |
|---|---|
| 公共脚本 | `python3` 3.10 或更高版本，以及项目声明的 Python 依赖 |
| 随附的 shell 与构建脚本 | Bash；lint/CDC 和仿真还使用 `make` |
| RTL 编译 | 支持任务所用 RTL 语言、源文件清单和 include 路径的编译器；RTL 阶段需编译完整文件集 |
| 功能仿真 | `vcs`、由 `UVM_HOME` 指定的 UVM 源码，以及与该 VCS 版本兼容的 C/C++ 工具链 |
| 结构覆盖率 | VCS 对所需覆盖指标的插桩能力，以及 `urg` 报告工具 |
| 波形采集与诊断 | 随附仿真脚本需要的 VCS/Verdi FSDB 支持；波形查询使用 `fsdbreport`，需要转换时使用 `fsdb2vcd` |
| Lint 与 CDC | `spyglass` 及阶段使用的 lint、CDC 检查能力 |
| 综合 | `dc_shell`，以及 `compile_ultra` 使用的 DC-Ultra 能力 |
| 静态时序分析 | `pt_shell` 及所需的时序分析能力 |
| 功耗实验与计算 | 实验使用的仿真器、单元模型及其他工作负载依赖；计算使用 `pt_shell` 及 PrimeTime-PX 功耗分析能力 |

规格与验证规划使用公共 Python 依赖，RTL 设计还需要编译工具。采用仍适用的已有活动数据重新计算功耗时，需要计算环境；编译和运行新实验时，还需要相应的仿真环境。

UVM 仿真中的 `UVM_HOME` 应指向构建所用的 UVM 发行目录，其中包含 `src/uvm_pkg.sv` 和 `src/dpi/uvm_dpi.cc`。随附仿真脚本接受可选的 `VCS_CC`、`VCS_CPP` 设置，通过 VCS 的 `-cc`、`-cpp` 选项指定 C、C++ 编译器。版本应与已安装工具的支持范围相符。

## 3. 提供库、模型与阶段配置

向阶段执行者提供库和模型的位置、用途，以及任务要求的分析条件。所需材料可能包括标准单元、存储器或其他宏单元的库与仿真模型，以及工作条件和互连估计。根据设计要求及库或模型提供方的文档确定适用资源与条件。用于网表链接和分析的库应覆盖网表中的单元，仿真模型也应与该实现匹配。

资源的存放位置由部署环境确定；选用库的工作条件、采用何种线负载模型，则取决于任务要求。执行者在阶段工作目录中记录实际使用的配置。当前主要入口如下：

| 工作 | 随附阶段的配置入口 |
|---|---|
| 综合 | `config.tcl` 提供 `LIB_DB`、`WIRE_LOAD_MODEL`；bootstrap 仅在文件不存在时从环境变量初始化这些值。 |
| 时序分析 | `config.tcl` 提供 `LIB_DB`，以及根据阶段输入确定的顶层和网表位置；bootstrap 仅在创建文件时读取环境中的库设置。 |
| 功耗计算 | 调用阶段 CLI 前，先加载工作目录中的 `env.sh`。`LIB_DB` 是链接库路径的 Tcl 列表，`STRIP_PATH` 指定 SAIF 数据中采集的 DUT 层次。 |
| 仿真与功耗实验 | 仿真的 `env.sh` 提供 `UVM_HOME` 和运行设置；功耗实验的编译、运行脚本负责提供仿真器、模型文件及工作负载配置。 |

修改已导出的变量不会更新已有 `config.tcl`。复用工作目录或更换资源时，应检查阶段实际生效的配置。

当前综合和时序模板将 `LIB_DB` 配置为单个 `.db` 路径。任务若需要额外链接库、宏单元或工作条件设置，需要相应调整阶段的工具配置；仅导出一个库列表不会改变这些模板的行为。功耗模板已经按 Tcl 列表读取 `LIB_DB`。例如，将下列路径替换为真实库后，可用于一次功耗计算：

```bash
export LIB_DB='{/path/to/cell-library.db} {/path/to/macro-library.db}'
```

列表只应包含本次计算需要的库。综合的 `WIRE_LOAD_MODEL` 应按任务采用的互连估计，设为所选库中实际存在的模型名，或显式设为 `none`。

`LIB_V` 可以用于指明已有的单元模型资源，但功耗 CLI 不会自动将它加入仿真器文件清单。实验的构建脚本需要包含实际所需的单元和宏模型。还需结合任务要求核对模型是否齐全、测量条件是否适用。

阶段配置细节见[综合](../skills/synthesis/SKILL.md)、[时序分析](../skills/timing-analysis/SKILL.md)和[功耗分析](../skills/power-analysis/SKILL.md) skills。

## 4. 检查是否可运行

在启用 VeriPower 的独立会话中提出：

> 使用 env-precheck skill 检查我计划开展的工作。从阶段实际使用的执行环境中检查，说明哪些工作可以运行、哪些检查失败，以及哪些尚未测试。

说明计划运行的阶段或计算，并提供所选资源的位置。预检查先探测工具与配置，再在临时目录中运行小型任务，检查相关许可证和执行过程。探测需要设置超时，避免许可证服务不可用时一直等待。

阅读报告时，关注实际执行了什么、产生了哪些输出，例如映射后的网表、时序报告、仿真输出、覆盖率报告或功耗报告。版本信息、许可证列表中的功能名称或零退出码，本身都不能证明环境已经可用。具体检查由 [env-precheck skill](../skills/env-precheck/SKILL.md) 规定。

解决环境问题后，重新检查受影响的部分。被跳过或未测试的项目仍未得到验证。工具版本、资源位置或执行环境变化后，应重新检查相关能力，并让 agent 重新评估受影响的已有测量结果。预检查只说明已测试配置的可运行性；实际任务及其结果仍需由相应阶段评价。预检查会报告问题并给出环境设置建议，不修改 shell 配置或模块文件。

## 5. 定位环境问题

根据失败工作的命令、执行位置、工具版本和日志定位原因。

| 现象 | 下一步检查 |
|---|---|
| 找不到命令，或 agent 中的行为与终端不同 | 检查 `PATH`、所选 Python 环境，以及实际执行进程加载的配置。 |
| 许可证检出失败或长时间等待 | 检查许可证配置、服务是否可访问，以及是否有权使用所需功能；重新执行有超时限制、会实际使用该功能的检查。 |
| 工具尚未读取设计就启动失败 | 检查安装版本的启动脚本解释器及支持的运行环境，采用适合该安装环境的配置方式；全局修改 `/bin/sh` 不是 VeriPower 的通用前提。 |
| VCS 在 C/C++ 编译或链接时失败 | 核对该 VCS 版本与编译器、链接器的兼容性；需要显式选择编译器时设置 `VCS_CC`、`VCS_CPP`。 |
| 找不到库、单元或模型 | 检查文件是否可见、实际生效的 `config.tcl` 或 `env.sh`，以及链接库和仿真文件清单是否覆盖实际设计。 |
| 工具已结束，但覆盖率或功耗报告不可用 | 先检查报告生成选项、插桩和分析范围，再解释结果；查看阶段的原始报告和日志。 |

结构覆盖率方面，随附脚本使用 `urg -format text`，并通过 `--cov-dir` 将报告目录传给解析器。解析器需要 `dashboard.txt` 和 `modinfo.txt`。检查所需覆盖指标是否在编译时启用，配置的 DUT 实例是否与设计一致。不支持的报告格式或缺失的测量不能满足覆盖率目标。解析细节见 [parse_coverage.py](../skills/simulation/templates/infra/scripts/parse_coverage.py)。

功耗方面，检查所选网表、库和约束是否与实验匹配，SAIF 是否覆盖预期活动与测量区间，以及 `STRIP_PATH` 是否对应采集的层次。报告包含数值，本身并不能证明测量有效。

设计任务的启动、复核和恢复见[用户指南](USER-MANUAL.zh.md)。
